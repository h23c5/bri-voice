# BriVoice · Android 歌声合成 / 调音

以本机安装的 **VOCALOID4 Editor（E:\V4，同好协会汉化版）** 为蓝本实现的安卓歌声合成与调音软件。
**本体不内置任何音色**：所有音色都来自你安装的外部声库（.v4voice），声库由电脑端工具从你自己授权的
VOCALOID4 声库生成。
纯 Java 8 + 原生 Android 框架编写，**不依赖 Gradle / AndroidX / 任何第三方库**，用自带的 `tools/build_apk.py`
直接调用 aapt2 / javac / d8 / zipalign / apksigner 打包成 APK。

## 五、歌姬与"添加声库"

### 用真实声库数据发声（v1.3 新增）

VOCALOID4 的 .ddb **不是采样拼接**，而是分析合成数据：每条 FRM2 记录 = 一帧频谱
（32 字节头 + 350 个谐波频率 k·f0 + 350 个谐波 dB 幅度，帧间隔恒为 256/44100 s ≈ 5.8 ms），
洛天依声库里 367,558 帧、初音未来 224,604 帧。

所以"把官方采样加进去"的正确做法是**用这些真实频谱帧做加法合成**，本版即如此实现：

1. 转换工具按 .ddi 的 64 位偏移目录抽样帧（洛天依 34.3 万条目录项），解码每条 FRM2 的谐波幅度；
2. 每帧按共振峰匹配到最接近的汉语音素（洛天依 86%、初音未来 90% 的帧可匹配）；
3. 按音高分 3 段（低/中/高）在线性域平均，得到**每个音素 × 每个音高段的实测谐波包络**
   （64 个对数频点、0.5 dB 量化）；
4. 应用端 HarmonicVoice 用该包络做**加法合成**：逆 FFT 生成一个周期的波表（Schroeder 二次相位分散，
   避免脉冲状波形的高波峰因数），再由相位累加器按音符 f0 读出——音色**直接来自声库本身**。

实测验证（HarmonicRenderCheck）：把渲染结果的谐波幅度与包里存的实测谱逐次谐波对比，
**相关系数 0.997 / 0.998**（14 次谐波）；音准 220.0002 Hz；与内置歌姬音量差 +1.9 dB。

包体积：洛天依 **7.1 KB**（49 音素 × 3 段 = 147 条曲线）、初音未来 **8.4 KB**（61 × 3 = 183 条）。
两个库的数据明显不同（同频点差 2.6–11.9 dB），例如音素 a 在 2082 Hz：洛 −33.0 dB、初音 −14.5 dB。

**诚实的边界**：
- 这**不是**逐音符复刻原软件的选帧结果。原软件用 .ddi 内部索引按歌词/音高/力度挑具体帧序列，
  该索引语义尚未完全解出；本实现是把这些帧的频谱**统计地**匹配到音素，再配本软件自己的
  连音/颤音/滑音/动态引擎。即：音色是声库的，选帧与表现力是本软件的。
- 谐波路径目前覆盖元音、鼻韵母等浊音；清辅音仍用内置噪声模型。我们扫描了 .ddb 中的 7,749 / 5,195 条
  SND 记录并聚类，结果 799/800 与 790/795 都是**浊音**（不是擦音噪声），故未当作擦音样本使用——
  这是一个有据可查的否定结论。
- 低于声库实测音域的音符，基频落在"该帧没有谐波"的区域，实现里用 6 dB/oct 从锚点向下延伸，
  不会出现空洞，但这段精度低于实测段。

### 本版音色改进（v1.5）：力度分层 + 帧数翻三倍

上一版每个音素只有**一条平均频谱**，所以同一音素每次听起来完全一样，DYN 也只改音量。本版把每个
音高段再按**帧能量**分成 3 档力度，得到实测的 soft / mid / loud 三条谱：

| | 音素 | 实测曲线数 | 包大小 |
|---|---|---|---|
| 洛天依 V4 中文·萌 | 49 / 62 | **441**（3 音高段 × 3 力度档） | 15.6 KB |
| 初音未来 V4 中文 | 61 / 62 | **549** | 22.4 KB |

合成时先按音高选段、再按 DYN 选力度档，于是：

- **DYN 曲线现在真正改变音色**，不只是音量；实测 soft→loud 的谱差 31（相对值），
  高频占比（2–8 kHz 对 200–800 Hz）从 −24.1 dB 升到 −20.6 dB —— 越用力越亮，
  这正是真实声库（以及人声）的行为。
- 同音素在不同力度/音高下不再千篇一律。

### 本版新增（v1.6）

**1. 文件管理器里「用 BriVoice 打开」**

已在 AndroidManifest 注册 VIEW 关联（实测系统可解析 `.mid` 与 `application/octet-stream` 两种来源）：
从文件管理器选「打开方式 → BriVoice」即可直接把工程或声库交给 BriVoice。

- `.vsqx` / `.vsq` / `.mid` → 直接打开工程（MIDI 自动导入成音符）
- `.v4voice` → 直接导入声库并选中它
- 现代文件管理器发的是 `content://`，这条路一定通；若某个管理器发 `file://`：`.mid` 属音频，
  授予「音乐和音频」权限即可读；`.vsqx` 不是媒体类型，应用会弹窗引导你去系统设置开「所有文件访问」。
  实测：授权前报分区存储限制，授权后 `已打开 test_import.vsqx（1 轨 / 3 音符）`。

**2. 修掉每个音前面的"爆破"**

原因有两个，都在渲染器里：

- **塞音爆破段被渲染成满幅脉冲**：`t/p/k` 等塞音的成阻爆破原本以音素满增益输出，峰值 0.077，比元音稳态还高，
  听起来就是每个字前面的"啪"。现在按真实语音比例压到 0.11（不送气）/0.22（送气），长度 6–10 ms，并加了 1.5 ms 上升沿防爆音：
  实测峰值 **0.077 → 0.019**。
- **元音比音符晚约 100 ms**：原来整个音节（含辅音）都塞在音符内部，元音自然迟到。现在辅音像 VOCALOID 那样
  **抢在音符起点之前**（最多 90 ms，且不会侵入前一个音符），元音正好落在拍点上：实测元音在音符起点后 35–40 ms 就到位（原 100 ms）。

**3. 导入 MIDI**

「打开」按钮现在接受 `.mid/.midi`，文件管理器直接打开也可以。真机实测 `His Theme.mid` → **7 轨 / 2054 音符**，
与独立 Python 解析出的 2054 个 note-on 完全一致（顺带修掉一个真 bug：`Song.copy()` 假定拍号数组长度为 4，
而 MIDI 导入给出长度 3，导致每次打开 MIDI 都抛 `ArrayIndexOutOfBoundsException`）。

### 本版（v1.7）：真实帧序列 + 二次修爆破

**1. 每个格子存的是真实帧序列，不再是一条平均谱**

| | 音素 | 格子 | 每格真实帧 | 包大小 |
|---|---|---|---|---|
| 洛天依 V4 中文·萌 | 49/62 | 441 | 12 | 132 KB |
| 初音未来 V4 中文 | 61/62 | 549 | 12 | 182 KB |

转换器把每个（音素 × 音高段 × 力度档）格子里的帧按**原始顺序**排好，取 f0 最接近该格子中位数的
连续一段（帧间隔正好 256/44100 s），连同每帧的相对电平一起写进声库。合成时按音符内的位置在这段
序列上插值，所以音色会随音符**演进**而不是钉死：实测一个长音内频谱平均变化 **3.71 dB**（洛）/
**6.96 dB**（初音），最大 12.9/13.7 dB。

**按上下文选帧实现三条轴**：音高（选 f0 最近的格子）→ 力度（按 DYN 选 soft/mid/loud 实测档）→
音符内位置（走真实帧轨迹）。第四条轴"音素身份"仍来自共振峰聚类（匹配率 86–90%），原因见下。

**2. `.ddi` 索引到底给了什么（结论）**

实测：`.ddi` 里能找到 **343,198 个 64 位偏移**，抽样 50/50 全部正好落在真实 FRM2 记录上——它是一个**帧定位表**。
但它（a）不是按文件顺序排的（排序后 343,197 个间隔全部不是"下一帧"），（b）**没有配套的逐帧音素标签表**
（全文件扫描没有任何"字节值全 < 62 的长数组"）。所以想精确到"这个帧属于哪个音素"，索引本身给不出，
只能像现在这样从频谱共振峰去测量归类。这条我会继续跟，但不夸口能解出来。

**3. 爆破：第二轮（真正的元凶）**

上一版压掉的是塞音的成阻爆破段。这次逐音节量了**辅音与元音的响度比**，发现所有噪声类辅音都**盖过元音**：

| 音节 | 修复前 | 修复后 | 高频峰值 |
|---|---|---|---|
| sa | **+4.8 dB**（峰值 0.376） | −6.9 dB | 0.092 → 0.023 |
| qi / za / sha / fa / ha | +0.9 … +2.8 dB | −6.4 … −10.4 dB | 0.20–0.25 → 0.06–0.16 |
| ma / la | +2.5 / +0.7 dB | −1.4 / −2.8 dB | — |
| ta / pa / ka | −10.6 dB（已正常） | −8.5 dB | — |

现在按发音方式配平：擦音/塞擦音 ≈ −7…−10 dB、鼻音/边音/介音 ≈ −1…−3 dB，与真实歌唱的比例一致。

**4. 顺手修掉一个严重的性能 bug**

帧序列一开始用 JSON 数字存，每个采样值一个装箱 Double：441 格 × 12 帧 × 64 点 ≈ 34 万个对象/包，
手机解析时 GC 抖动到 **721 MB、启动卡 30 秒以上**。改成 base64 + int8（0.5 dB 量化）后：解析 **502/583 ms → 154/96 ms**，
包 409 KB → **132 KB**，真机启动 **2.2 秒**、内存 433 MB。

### 本版（v2.0）：一个阻塞 bug + 五项新功能

**0. 修掉真机上"声库无法导入"**

导入路径本身没问题（流是循环读到 EOF 的），问题在**真机给的文件流经常是空的**（云盘占位文件、
被撤销的授权、文件管理器"最近"里的条目），而旧代码把所有失败都归成一句"不是 .v4voice 文件"，
于是所有人都在怀疑文件格式。现在：

- 先嗅探前 4 字节，再决定怎么解析。空流 / 内容不足 / 不是 ZIP 也不是 JSON 各有**明确的报错**，
  并把实际收到的开头字节打出来（实测：`不是声库文件：开头是 74 68 69 73（前 32 字节: ...）`）。
- ZIP 里找不到 voice.json 时，直接列出**实际条目名**；嵌套目录、大小写不同的 voice.json 都接受。
- 额外接受**未压缩的声库**（直接以 `{` 开头的 JSON）。
- 新增「声库 → **从文件夹批量导入**」：SAF 目录授权后一次导入文件夹里所有 .v4voice，
  真机上比单文件选择稳得多（这也是失败对话框里的默认建议）。

**1. 中英日三语**

### 本版（v3.0）：修掉参数曲线拖动的「梳齿」

- **实测**：200 次抖动事件（12 tick 范围内）现在只产生 **2 个点**（原来 200 个）；
  真机 16 次来回拖动后曲线是干净的三角峰。缓慢扫绘仍保留完整分辨率（40 点跨 2400 tick 一个不少）。

### 本版（v3.4）：修双轨渲染的 ArrayIndexOutOfBoundsException

报错内容：`渲染失败: java.lang.ArrayIndexOutOfBoundsException: length=99225; index=122598`。

**根因**：渲染缓冲区是按片段存的 `dur` 分配的，而**音符可以落在 `dur` 之外**——新建音轨时 `Part.dur` 是默认值，
在卷帘里画的音符不会自动把它撑大（第二轨最容易踩到；外部程序写的 .vsqx 也可能这样）。呼吸声效果按「音符间隙」
往缓冲区写数据时，位置来自音符（122598），越过了缓冲区末尾（99225），于是抛异常。

**修法**（三层）：
1. 分配缓冲区时取 `max(片段 dur, 所有音符的结束 tick)`；
2. 呼吸声写入加边界保护（`idx < 0 || idx >= out.length` 就跳过）；
3. 编辑时同步维护 `Part.dur`——加音符、拖长度都会把 dur 撑到覆盖所有音符，新工程不再产生这种数据。

**验证**：新增 PartDurTest——故意把 `dur` 设成 480 而音符排到 tick 21120，现在渲染出 981,225 采样（需要 ~970,200）、
不抛异常且非静音；真机双轨工程完整播放 5 秒、无报错（logcat 干净）。

### 本版（v3.5）：删除音符后立刻又被重建

**原因**：卷帘里「在空白处轻点 = 新建音符」，而这个判定只检查了「没有移动」，**没有检查按了多久**。
所以任何在空白处的抬手——包括长按——都会在落点新建一个音符；删除后的抬手自然就「把刚删掉的音符又建回来」。

**修法**（两道闸）：
1. 只有**短按**（时长小于长按阈值）在空白处才会新建音符，长按不再误建；
2. 删除动作（长按删除 / 双击撤销刚建的音符 / 删除选中）都会记录时间戳，**删除后 400ms 内的新建一律忽略**。

**验证**（真机）：卷帘空白处轻点 → 状态栏「编辑: add la」（仍能新建）；同一位置长按 900ms → 状态栏不变，**没有再建一个音符**

### 本版（v4.7）：指针跟声音对齐 + 拖动片段不再重置视图

**1「指针太快、声音出来时已经到第 5 个音」**

先做了实测（通过接口每 250 ms 采一次播放位置）：指针速度**是正确的**——120 BPM 下约 960 tick/秒，与节拍一致。
所以问题不是速度，而是**指针比听到的声音早**。原因：引擎用墙钟推算位置，没有算设备输出缓冲。

改动：指针改为跟随 **AudioTrack 的实际播放头位置**（`getPlaybackHeadPosition`），并以墙钟为上界（保证不会往前跳）。
实测改后指针落后约 76 ms（= 设备缓冲）。

**但如果你的设备（模拟器/蓝牙）输出延迟远大于缓冲**，应用无法自己测到那段时间——所以设置里新增
「**指针延迟补偿**」滑块（0–1000 ms，默认 0）：听到的声音比画面慢多少，就把它拉回多少。

**2「拖动 WAV 音频时会重置轨道位置」**

根因找到：`PianoRollView.setSong()` 会把滚动位置归零并重设缩放，而**每次编辑后的 `refreshAll()` 都会调它**——
所以一松手（提交拖动）视图就跳回开头。现在新增 `setSongKeepView()`（记住并恢复滚动/缩放），编辑路径改用它；
只有真正加载工程时才重置视图。

**验证（真机）**：先把视图拖到第 3–4 小节，再拖动片段 → `startTick` 由 0 变 **1680**（状态栏「移到 001:4 01.75s」），
而**视图仍停在第 3–4 小节**（前后截图一致）✓。

### 本版（v4.8）：实时渲染播放（不再等整首渲染完）

以前按播放要**先把整首歌渲染完**才开始出声（手机上很慢）。现在改成**边渲染边播**：

- 后台先渲染 **1 秒**就开始播放，随后按 1→2→4→8… 秒递增继续渲染（总工作量约为整首的 2 倍，但开声时间从「整首」降到约 1 秒）；

**实测（真机，100 秒长、200 个音符的工程）**：

**已知取舍**：每次递增都会从 0 重渲染（因此总 CPU 约为整首的 2 倍，换来的是立即开声）；
内存仍是整首的立体声缓冲（与之前相同）。若你的工程特别长（比如 10 分钟）想进一步省内存，我可以改成环形缓冲。

### 转换步骤（在你自己的电脑上、用你自己的授权声库）

### 添加声库（.v4voice）

应用本身只内置参数化音色，但支持**导入你自己声库的参数包**：

1. 在电脑上（本机）运行转换工具，从你已购买的声库中提取音色参数：
   ```powershell
   python tools/voicebank_pack.py --bank "E:\LuoTianyiV4_CHN\BK8H76TAEHXWSKDB" --out build/voicepacks --clusters 40
   python tools/voicebank_pack.py --bank "E:\VoiceDB\MikuV4C\BNGE7CP7EMTRSNC3"  --out build/voicepacks --clusters 40
   ```
   工具读取 `.vvd`（XOR 0x1A 文本）取声库身份、`.ddi` 的 PHDC 音素表与 64 位偏移目录、
   `.ddb` 的 FRM2 频谱帧（每帧 = 32B 头 + 350 个谐波频率 + 350 个 dB 幅度），
   得到：**每个汉语音素的 F1/F2/F3 实测值**（洛天依 60/62、初音 61/62 个音素匹配成功）、
   **整库平均频谱包络（7 段 EQ）**、f0 统计与音色参数。
2. 把生成的 `.v4voice`（2–3 KB）传进手机，应用里点 **声库 → 导入声库文件**。
3. 导入后在 **歌手** 列表里以 `[我的声库]` 出现，可随时删除。

包里**只有参数**（共振峰、EQ 曲线、统计），**不含任何官方采样/帧数据**，也不含 `.ddb` 的任何内容；
转换在你自己的机器上用你自己的授权声库完成，不涉及再分发。详见 [docs/voicepack-format.md](docs/voicepack-format.md)。

实测差异（同一乐句，真机导出 WAV 对比内置洛天依 vs 导入的洛天依包）：
60–200 Hz **+7.8 dB**、800–2500 Hz **+9.4 dB**、2500–6000 Hz **−9.4 dB**，整体相对差异 1.04 —— 音色确实变了。

### 内置歌姬（参数化合成，非官方采样）

| # | 名称 | 语言 | 说明 |
|---|---|---|---|
| 1 | **洛天依 V4 中文 · 萌** | 中文 | 明亮清透的少女声线（对应本机 Luo Tianyi V4_Meng 的音域/音色走向） |
| 2 | 初音未来 V4 中文 | 中文 | 更亮、更靠前、气息更少（对应 Miku V4 CHN） |
| 3 | 洛天依 · 柔（抒情） | 中文 | 气息更重、音色更暗的抒情变体 |

**关于"内置歌姬"的实话**：本机安装的洛天依 V4_Meng（`.ddb` 4.1 GB）与初音未来 V4 CHN（`.ddb` 2.4 GB）
是 Yamaha 的**专有采样声库**，既不能重新分发，手机端也无法直接解码（采样数据 + 未公开的合成模型）。
因此内置歌姬是**自研的参数化声码器**：用汉语音素的共振峰模型 + 声门源 + 清浊噪声合成歌声，
再按两位歌姬的音色走向（共振峰整体位移、谱倾斜、气息量、颤音）做区分。
它**不是**官方采样音色，但完全可听、可调、可导出，且与官方格式同一套音素与参数体系
（汉语 62 音素表与拼音映射直接取自本机 `g2pa4_CHS.dll` 与声库 `.ddi`，
写进 .vsqx 的 `<p>` 就是官方编辑器能识别的音素串，例如 `tian` → `t_h iE_n`、`xiao` → `s\ iAU`）。

## 七、代码结构

```
app/src/com/dsh/v4tune/
  model/     Song Track Part Note Voice ControlCurve TimeUtil     数据模型（VSQX 语义）
  format/    VsqxReader/VsqxWriter  Vsq2Reader/Vsq2Writer  MidiReader
  phoneme/   PhonemeDef PhonemeTable ChineseG2P JapaneseG2P PinyinDict
  synth/     VoiceSource FormantFilter Noise WavWriter VoiceModel SingerLibrary Renderer
  audio/     AudioEngine（渲染/混音/AudioTrack 播放/WAV）  Demo（示例工程）
  io/        ProjectIO（SAF 打开/保存/导出/分享）
  ui/        PianoRollView ParamView Theme
  MainActivity.java
tools/       build_apk.py 与全部自测（render_test / g2p_selftest / dsp_selftest / format_selftest / legacy_selftest）
```

**合成链路**：谱面 → 按音符切音素段（声母/韵母/韵尾）→ F0 曲线（音高 + PIT/PBS 弯音 + 颤音 + 滑音）→
声门源（Rosenberg 开相 + LF 指数回归，8× 过采样）+ 气息噪声 → Klatt 五共振峰级联 + 鼻音零点 + 擦音并联带通 →
包络/动态 → 立体声混音（轨道音量/声像）→ 软限幅。
实测渲染速度约 **24–49× 实时**（44.1 kHz 单声道），手机上 3 分钟的歌几秒渲染完。

## 七点五、本版变更（1.4）

- **改名 BriVoice**（应用名 / 标题 / 关于页）。
- **删除全部内置歌姬**：本体不再带任何音色。启动时若没装声库，会明确提示并引导导入；
  按播放/试音/琴键试听前会检查，没声库就弹窗指引，不会静默出怪声。
- **声库改放外部存储**：`/sdcard/Android/data/com.dsh.v4tune/files/voicebanks/`，
  单个声库上限放宽到 **2 GB**；旧版本装在内部目录的声库会自动迁移。
- **歌手列表直接显示声库含有什么**：例如「实测谐波 49 音素/147 频段」；
  没有实测谐波的旧格式包会标 ⚠ 提醒（那种包只有共振峰参数，听起来和内置模型差不多）。
- 音色不再受"当前选中的是内置歌姬"影响——因为已经没有内置歌姬，装了什么就用什么。

> **为什么你上次觉得"音色没变"**：上一版仍有内置歌姬，且默认选中的是内置的"洛天依"。
> 只导入声库并不会自动切换过去，播放用的还是内置模型，所以听不出差别。
> 1.4 起不存在这个问题：装了哪个声库，发出来的就是哪个声库的声音。
> 另外旧版导入的声库包（2.4 KB，只有共振峰+EQ）需要**重新导入**新的包（7–8 KB，含实测谐波）。

## 八、本版修复记录（1.2）

| 问题 | 原因 | 处理 |
|---|---|---|
| 每次开始播放先响一声"钢琴" | 渲染器包络在音符开始前算出了**负增益**（`i < s0` 时 `(i-s0)/atk` 为负且很大），把脉冲串整段漏了出来，听起来像一记衰减的音符 | 包络在段外一律返回 0；实测开头 0.5 s 由 RMS 0.60 变为 **0.0000** |
| 重做键失灵 | 撤销快照是在**编辑之后**才拍的，撤销恢复的其实是编辑后的状态；重做因此没有可重放的历史 | 改为"提交前快照"模型（`baseline`），撤销/重做对称；真机验证 添加→撤销→重做→再撤销 全通 |
| 播放/画面不同步、按钮提前变回"播放" | `AudioTrack` 会瞬间吃下整个缓冲区，写完即回调 onDone；且播放头位置取自写入量而非实际播放量 | 写完后按**墙钟**播完剩余时长再报完成，进度也按墙钟计算；真机日志 `elapsedMs=11016 / totalMs=11000`，界面位置随声音推进 |

## 九、限制

1. **不含官方声库**：见第五节；如需要官方音色，请在你自己的设备上用官方编辑器导出 WAV，或后续自行接入合法声库。
2. **VOCALOID2 .vsq** 无本机样本可对照，字段表来自官方导出插件，属"有据可依但未对照真实文件"。
3. 合成音质是"参数化歌声合成"水平：元音清晰、音高准确、辅音可辨，但不如官方采样声库自然；
   颤音/滑音/动态/气息等**表现力参数都已生效**，可当作编曲草稿与教学工具使用。
4. 双指缩放手势无法用 adb 注入多点触控，只在代码层面审查过；单指全部交互已在真机验证。
5. 未做 PNG 图标适配（仅提供传统 mipmap），部分启动器上图标偏小。
